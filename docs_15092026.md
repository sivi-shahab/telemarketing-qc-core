# Perbandingan `4-service-telemarketing-qc-system/core` vs `telemarketing-qc-core`

Tanggal: 15 September 2026
Status: **dokumen review — belum ada kode yang diubah.**

Tujuan dokumen ini: memetakan SELURUH perbedaan antara paket `core` di dalam repo
monolit `4-service-telemarketing-qc-system` (selanjutnya **A**) dan paket pip
`telemarketing-qc-core` / `src/qc_core` (selanjutnya **B**), supaya bisa diputuskan
apa yang harus di-port dan ke arah mana, SEBELUM implementasi.

---

## 1. Ringkasan eksekutif

A dan B **bukan versi lama vs versi baru**. Keduanya adalah **dua garis
pengembangan yang bercabang dari titik yang sama lalu jalan sendiri-sendiri**.
Masing-masing punya fitur yang tidak dimiliki yang lain.

| | A — `4-service-.../core` | B — `telemarketing-qc-core` |
|---|---|---|
| Bentuk | folder di dalam monolit, di-copy datar ke image | distribusi pip `telemarketing-qc-core` 1.0.0 |
| Namespace impor | `core.*` | `qc_core.*` |
| Commit terakhir | `1ccd74c`, 14 Sep 2026 | `5ba19ad`, 8 Sep 2026 |
| Sumber reference data | PostgreSQL (`tms_cashline`, `ascend_custp`) | **DWH API Aplikasi A** (`services/data_dwh.py`) |
| Object storage | SDK `minio` (lewat `api.dependencies`) | **boto3 multi-bucket** (`services/s3_buckets.py`) |
| Alembic | ada di `core/db/migrations` (52 revisi) | tidak ada (pindah ke repo `telemarketing-qc-api`) |
| CI | Jenkins/monolit | GitHub Actions + guard "core tidak boleh impor api/worker" |
| Tes | 11 file | 9 file |

**Titik cabang: `aa7d82b` (14 Agustus 2026).**
Sesudah itu:

* **A** melanjutkan di repo `4-service-...` sendiri — restrukturisasi
  `api/core/worker/dashboard` (2 Sep) lalu **fitur QC baru 5–14 September**.
* **B** dipisahkan dari `telemarketing-qc-system` cabang `dev`, disinkronkan
  terakhir dari `dev@fa2c268` (**2 September 2026**), lalu melanjutkan sendiri
  dengan pekerjaan **infrastruktur** (boto3, packaging, CI) sampai 8 September.

Akibatnya ada **dua arah utang port**:

* **A → B (12 hari fitur QC belum masuk paket).** Semua pekerjaan 5–14 September.
* **B → A (infrastruktur belum masuk monolit).** DWH API, boto3 multi-bucket,
  proxy Aplikasi C, `campaign_kind`, placeholder roster.

> Catatan memori proyek: `tms_cashline` lokal sudah kosong dan pembacaannya
> harus lewat `crud.cashline_agent_index()`. Jalur itu **hanya ada di B**.
> Artinya A secara operasional sudah tidak bisa membaca reference data di
> lingkungan sekarang — ini menentukan arah merge (lihat §6).

## 5. Risiko yang harus diselesaikan sebelum implementasi

1. **Tabrakan revisi Alembic `0052`.**
   `4-service/core/db/migrations/versions/0052_result_current_stage.py` dan
   `telemarketing-qc-api/db/migrations/versions/0052_perm_tl_qc_upload_sales_database.py`
   sama-sama `revision = "0052"`, `down_revision = "0051"`. Revisi 0001–0051
   identik di kedua sisi. Salah satu **harus** dinomori ulang (mis. `current_stage`
   menjadi `0053`) sebelum digabung, atau `alembic upgrade head` akan gagal.
2. **Arah reference data.** `reference_data.py` + `crud.py` A dan B tidak bisa
   digabung baris-per-baris — sumbernya beda (DB vs DWH API). Harus dipilih satu:
   jalur DWH API milik B (yang sesuai kondisi produksi, karena `tms_cashline`
   lokal sudah kosong).
3. **Ketergantungan silang.** CI B menolak `from api`/`from worker` di `src/`.
   Beberapa modul A (mis. `parallel_pass`, `two_pass`, `recording_type`) perlu
   dicek dulu apakah menarik sesuatu dari `api`/`worker`; kalau ya, bagian itu
   harus dipisah sebelum masuk paket.
4. **Perubahan bentuk prompt.** `_build_user_content` A mengubah URUTAN blok
   prompt. Isinya sama, tapi bentuk prompt yang berubah bisa menggeser perilaku
   model — wajib diuji dengan reprocess pembanding, bukan hanya unit test.
5. **`documents.py`.** Port dari A tidak boleh mengembalikan `sys.path` hack yang
   sudah dibuang B di `50cf7d6`.
6. **Aturan distribusi (memori proyek).** Distribusi ke repo split dilakukan
   **aditif**, tidak pernah wholesale copy — repo monolit `telemarketing-qc-system`
   tetap read-only.

## 6. Usulan arah (untuk didiskusikan, belum dikerjakan)

**B adalah basis, A adalah sumber fitur.** Alasan: B sudah sesuai arsitektur
produksi (DWH API, boto3 multi-bucket, proxy App C, tanpa impor `api`), sudah
berupa wheel ber-CI, dan sudah dikonsumsi repo api + worker. Membawa infrastruktur
B ke A berarti mengulang pekerjaan 8 September di tempat yang salah.

Urutan port A → B yang diusulkan (paling mandiri dulu, paling berisiko terakhir):

| # | Batch | Isi | Risiko |
|---|---|---|---|
| 1 | Utilitas murni | `static_similarity` (`_SPELLING_CLARIFIER`), `pdf_parser` (`sort_pdf_paths`), `ocr` (`image_bytes_to_pdf`) + tes | rendah |
| 2 | Nama on-air | blok `call_ownership` + `test_agent_name` | rendah |
| 3 | MUS | `mus_exemption.{py,json}`, `scoring`, `prompt/ocr_mus_exception` + 2 tes | sedang |
| 4 | Dokumen & error code | `documents`, `error_codes`, `stats_aggregate` (gabung dengan `_avg*` milik B) | sedang |
| 5 | Jenis recording & multi-pass | `recording_type`, `two_pass`, `parallel_pass`, `prompt/pass2` | tinggi |
| 6 | Evaluator & caching | urutan blok prompt + `reference_text` + `cached/reasoning token` | tinggi — butuh reprocess pembanding |
| 7 | `current_stage` | `db/models.py` + `crud.set_result_stage` + migrasi **dinomori ulang** | tinggi — sentuh skema |

Yang TIDAK di-port dari A: `services/`-nya tidak ada, `config/base.py` (digantikan
`core_config.py`), `db/migrations`, `db/seed`, `scripts/`, `requirements.txt`,
`.env.example` — semuanya milik repo api/worker, bukan paket core.
`crud.get_ascend_custp_by_local_name` dan seluruh jalur `tms_cashline`/`ascend_custp`
juga **tidak** di-port: sudah digantikan jalur DWH API.

Yang perlu jalan sebaliknya (B → A) hanya bila repo `4-service-...` masih mau
dipertahankan hidup; kalau repo itu memang akan dipensiunkan setelah fiturnya
diserap, langkah ini tidak perlu sama sekali. **Ini pertanyaan pertama yang perlu
dijawab sebelum batch 1 dikerjakan.**

# BAGIAN II — Rencana port A → B (tanpa menyentuh fondasi B)

Ditambahkan 15 September 2026, setelah pemeriksaan lanjutan atas §7.
**Belum ada kode yang diubah.** Bagian ini menjawab: *apa saja yang perlu
di-update, dan apa yang harus diputuskan lebih dulu.*

## 8. Definisi "fondasi B" yang TIDAK boleh tersentuh

Delapan hal berikut adalah milik B dan tidak boleh tergeser oleh port apa pun:

1. Namespace `qc_core.*` dan layout `src/` + `pyproject.toml` + CI.
2. Guard CI: `src/` tidak boleh `from api` / `from worker`.
3. Reference data dari **DWH API** (`services/data_dwh.py` + `crud`), bukan
   `tms_cashline` / `ascend_custp`.
4. `services/s3_buckets.py` (boto3 multi-bucket) sebagai pengganti SDK `minio`.
5. `services/tickets_daily.py` + `services/view_streams.py` (proxy Aplikasi C).
6. `core_config.py` (`CoreSettings`, `get_minio`) — bukan `config/base.py` milik A.
7. `compliance/campaign_kind.py` dan `compliance/sales_roster.person()`.
8. Di `stats_aggregate.py`: sumber `submit_time`/`agent_id` dari
   `crud.cashline_agent_index()` / `crud.reference_snapshot_index()` (snapshot
   `reference_data`), serta `_avg` / `_avg_of` (Avg Failure Rate ÷ Total Recording).

## 9. Hasil pemeriksaan kelayakan (menutup §7)

**9.1 Tidak ada modul kandidat yang mengimpor `api` / `worker`.**
Seluruh `core/` A bersih kecuali satu baris di `stats_aggregate.py`
(`from api.sales_lookup import ...`) — dan B sudah menggantinya dengan
`from qc_core.sales_lookup import ...`. Jadi guard CI B tidak akan terlanggar.

**9.2 Ketergantungan `crud` dari modul kandidat semuanya sudah ada di B.**
Satu-satunya yang hilang, `crud.get_ascend_custp_by_local_name`, hanya dipakai
jalur DB lama di `reference_data.py` A — dan jalur itu memang **tidak** di-port.

**9.3 Pada file QC-logic, A adalah SUPERSET B — bukan versi lain.**
Diperiksa per fungsi (`documents.py`, `error_codes.py`, `scoring.py`): hampir
seluruh baris unik B hanyalah kalimat docstring yang ditulis ulang di A.
Pengecualiannya ada satu (lihat §11.1). Artinya file-file itu boleh diambil
**utuh** + ganti namespace, tidak perlu merge baris-per-baris.

**9.4 `stats_aggregate.py` adalah SATU-SATUNYA file yang tidak boleh diambil utuh.**
B punya ~120 baris unik yang merupakan fondasi (poin 8 di atas). File ini wajib
di-merge per fungsi.

**9.5 Modul baru A belum punya pemanggil di repo split.**
`parallel_pass`, `two_pass`, `recording_type`, `mus_exemption`,
`agent_name_verdict`, `current_stage` dipanggil dari
`api/routers/{transcript,stats,reprocess}.py` dan
`worker/tasks/process_transcript.py` di repo A. Di `telemarketing-qc-api` /
`telemarketing-qc-worker` belum ada satu pun pemanggilnya. **Port ke core saja
tidak mengubah perilaku apa pun sampai kedua repo itu ikut diperbarui.**

## 45. Aturan yang dikunci test: Auto Assign membagikan SISA

`bulk_assign_tickets_to_qc` sengaja TIDAK memanggil `assign_ticket_to_qc`, karena
fungsi itu MENIMPA assignment yang ada dan commit per tiket. Tombol Auto Assign hanya
boleh membagikan tiket yang belum dibagi — menimpa berarti memindahkan tiket yang

Aturan itu tidak terlihat dari tanda tangan fungsinya dan **tidak ada test yang

# BAGIAN XII — Pembuktian bentuk prompt tanpa LLM

## 49. Dua dari tiga langkah §39 sudah terjawab

`tools/bandingkan_bentuk_prompt.py` membandingkan bentuk prompt LAMA dan BARU atas
**10 tiket nyata (44 PDF, `data_transcripts/raw/sources`)** tanpa memanggil model sama
sekali. Dua dari tiga langkah di §39 karena itu tidak perlu lagi menunggu reprocess.

### Langkah 2 — "isinya sama, hanya letaknya yang berubah": TERBUKTI

Blok KB, SCORECARD, TRANSCRIPT dan teks reference sama **byte-per-byte**. Satu-satunya
tambahan teks adalah **label blok `REFERENCE DATA:` — 16 karakter** yang dulu tidak ada:
reference data dulu menempel di ekor SCORECARD tanpa judul sendiri. Selisih panjang
prompt terukur persis `+16`, konsisten di kesepuluh tiket.

Ini bukan kerapian belaka. Kalau isinya ternyata berubah, perbedaan hasil model nanti
tidak bisa lagi diatribusikan ke urutan saja — dan seluruh reprocess pembanding
kehilangan artinya.

### Langkah 3 — "`cached_token` harus naik tajam": TERUKUR sebagai prediksi

Panjang awalan yang sama antar-tiket berurutan, persis yang ditagih lebih murah:

```
bentuk LAMA :      108 karakter  ( 0% dari prompt)
bentuk BARU :   82.611 karakter  (71% dari prompt)
selisih     :  +82.503 karakter
```

Sesudah deploy, `cached_token` sungguhan tinggal dibandingkan dengan angka ini.

### Langkah 1 — perbandingan VONIS model: MASIH HARUS DIJALANKAN

Reprocess sekumpulan kecil tiket dengan kedua bentuk, lalu bandingkan
`scorecard_result` **per item**, bukan hanya skor akhirnya.

Tidak bisa dikerjakan dari lingkungan kerja ini: database yang terjangkau dari container
yang berjalan (`POSTGRES_DB=da`) **nol baris `results`**, dan kedua Postgres uji
(`qc-test-pg`, `qc-test-pg2`) belum punya tabel `results` sama sekali. Ia juga menuntut
panggilan LLM berbayar ke endpoint Bank Mega.

## 50. Batas alat ini — dibaca sebelum memercayai angkanya

**KB dan scorecard dibuat TIRUAN** seukuran yang tercatat (~97k dan ~15k karakter),
karena isinya ada di database campaign, bukan di repo. Yang diuji struktur dan
kestabilan awalannya, bukan isi KB-nya. Persentase 71% akan bergeser sedikit dengan KB
sungguhan; kesimpulannya tidak — awalan yang tadinya 0% menjadi mayoritas prompt.

**Percobaan pertama alat ini salah.** Ia melaporkan "ISI BEDA" pada SCORECARD di
kesepuluh tiket. Penyebabnya bukan kodenya yang diuji, melainkan alatnya sendiri: ia
merangkai ulang bentuk lama (`scorecard + "\n\n" + reference`) lalu ikut membandingkan
satu baris kosong penyambung buatannya sendiri. Perbandingannya diubah menjadi **per
bagian** — KB, TRANSCRIPT, scorecard, dan reference masing-masing dibandingkan langsung
ke sumbernya — dan barulah hasilnya bisa dipercaya.

**Tidak ada test otomatis untuk alat ini.** Ia butuh PDF transkrip nasabah yang memang
tidak boleh ikut ter-commit (lihat `.gitignore` dan alasan `skipif` di
`tests/test_pdf_parser.py`), jadi ia dijalankan manual dengan menunjuk folder transkrip.
